# Неделя 1. Linux, SSH и первый запуск API

Цель недели — научиться входить на Linux-сервер, понимать права доступа и процессы, а затем запустить API бронирования на одной VM с PostgreSQL. Проверка пройдена: после перезагрузки обе службы были `active`, а `GET /ready` вернул `200 OK` и `{"status":"ready"}`.

## 1. SSH и навигация

Команда `ssh ec2-user@<IP_VM>` выполняется на Mac. Слева от `@` — пользователь на сервере, справа — его адрес. После входа команды в этом терминале выполняются на VM. В приглашении вида `[ec2-user@имя-VM ~]$` до `@` стоит пользователь, после — имя машины, а `~` означает домашний каталог. Само приглашение вводить не нужно.

| Команда | Что делает |
| --- | --- |
| `whoami` | Показывает, от чьего имени выполняется команда. При первом входе получили `ec2-user`. |
| `pwd` | Печатает полный путь к текущему каталогу. Получили `/home/ec2-user`. Начальный `/` — корень дерева каталогов. |
| `ls` | Показывает имена файлов и каталогов в текущей папке. |
| `ls -a` | Включает имена, начинающиеся с точки. `.` означает текущий каталог, `..` — родительский. |
| `cd ..` | Меняет текущий каталог на родительский. Из `/home/ec2-user` это `/home`. |
| `cd ~` | Возвращает в домашний каталог. Bash раскрывает `~` в путь к дому текущего пользователя. |

## 2. Владелец, группа и права

Команда `ls -ld ~ ~/.ssh ~/.ssh/authorized_keys` показала две папки с правами `drwx------.` и файл `authorized_keys` с правами `-rw-------.`. `-l` включает подробный формат, а `-d` показывает свойства самой папки. Пара имён `ec2-user ec2-user` означает владельца и группу файла, у которых в данном случае одинаковое имя.

Первый символ показывает тип: `d` — каталог, `-` — обычный файл. Следующие девять символов делятся на три группы: владелец, группа файла, остальные. Завершающая точка в нашем выводе относится к контексту SELinux и стоит после этих десяти символов.

| Право | Вес | Обычный файл | Каталог |
| --- | --- | --- | --- |
| `r` | 4 | Читать содержимое | Читать список имён |
| `w` | 2 | Менять содержимое | Менять записи каталога, например создавать файлы при наличии `x` |
| `x` | 1 | Запускать файл | Проходить через каталог и обращаться к объектам по имени |

Вес складывается отдельно для каждой тройки. `700` даёт владельцу `rwx`, `600` — `rw-`, `400` — `r--`. У файла с `640` владелец получает чтение и запись, группа — чтение, остальные — никаких прав. В выводе `ls` это `-rw-r-----`. Чтобы прочитать файл по пути, требуются также права прохода по родительским каталогам.

Для практики создали пустой файл командой `mktemp ~/linux-practice.XXXXXX`. Шесть `X` заменяются случайными символами. В следующих командах нужно подставлять путь, который напечатал `mktemp`:

- `ls -l ПУТЬ` показывает исходные права.
- `chmod u-w ПУТЬ` убирает запись у владельца: `u` — владелец, `-` — отнять, `w` — запись. Получили `-r--------`, то есть `400`.
- `chmod u+w ПУТЬ` возвращает запись. `chmod 640 ПУТЬ` задаёт права сразу для всех трёх категорий.
- `stat -c '%a %n' ПУТЬ` показывает права цифрами (`%a`) и имя (`%n`). `-c` задаёт формат.

## 3. Пользователи, sudo и второй SSH-вход

`id` показал `uid=1000(ec2-user)`, `gid=1000(ec2-user)` и дополнительные группы `adm`, `wheel`, `systemd-journal`. UID — номер пользователя, GID — номер основной группы, а `groups` перечисляет группы целиком. `root` — отдельная учётная запись с UID 0. У `ec2-user` есть административный доступ через `sudo`.

`wheel` — группа, которой можно выдать права через настройки sudo. `sudo -l` перечислил применимые разрешения и показал `(ALL) ALL` и `(ALL) NOPASSWD: ALL`. Последнее совпавшее правило позволяет этому пользователю запускать любые команды от имени любого пользователя без пароля. Сам список разрешений не показывает, какая строка была выдана через группу, а какая напрямую.

Проверили это командами `whoami`, `sudo whoami`, `whoami`. Получили `ec2-user → root → ec2-user`. Bash остался под `ec2-user`, а `sudo` запустил только указанную команду под `root`. `id -u` и `sudo id -u` позволяют проверить ту же разницу по числовым UID.

Создали отдельного пользователя для запуска приложения:

```bash
sudo useradd -m learner
sudo install -d -m 700 -o learner -g learner /home/learner/.ssh
sudo ls -ld /home/learner/.ssh
sudo install -m 600 -o learner -g learner \
  ~/.ssh/authorized_keys /home/learner/.ssh/authorized_keys
```

- `useradd -m` создаёт учётную запись и домашний каталог. Без `-m` создание папки зависит от `CREATE_HOME`. `-M` явно запрещает создание. Путь к дому может быть записан даже при отсутствии самой папки.
- `useradd -s /bin/bash` явно выбирает Bash как оболочку входа. `useradd -D` показывает настройки по умолчанию. `id learner` проверяет уже созданную запись.
- `usermod -aG ГРУППА ПОЛЬЗОВАТЕЛЬ` добавляет существующего пользователя в дополнительную группу. `-G` задаёт список групп, `-a` добавляет его к прежнему списку. В этом упражнении дополнительные группы для `learner` не нужны.
- У `install` флаг `-d` создаёт каталог. Без него команда копирует файл из первого пути во второй. `-m` задаёт права, `-o` владельца, `-g` группу. Bash раскрывает `~` до запуска `sudo`, поэтому источником был файл `ec2-user`.
- `authorized_keys` содержит публичные ключи, которым разрешён вход. Приватный ключ остался на Mac. Обратная косая черта в конце строки продолжает команду на следующей строке.

Оставили административный сеанс открытым и из нового локального терминала успешно вошли через `ssh learner@<IP_VM>`. Позже запуск `sudo dnf install` под `learner` привёл к запросу пароля и был отменён через **Ctrl+C**. Запрос пароля сам по себе не подтверждает наличие разрешения. Системные пакеты ставили под `ec2-user`, а приложение собирали и запускали под `learner`.

## 4. Процессы и ресурсы VM

Процесс — запущенный экземпляр программы. Ядро присваивает ему PID, чтобы различать экземпляры даже с одинаковыми именами. PPID — номер текущего родителя процесса. PID после завершения процесса может использоваться снова.

```bash
ps
ps -p "$$" -o pid,ppid,user,comm
ps -p 25201 -o pid,ppid,user,args
```

В нашем сеансе Bash имел PID `25202`, его родитель `25201` отображался как `sshd-session: learner@pts/1`. Эти номера относятся только к тому сеансу. `$$` подставляет PID оболочки, `-p` выбирает конкретный номер, `-o` задаёт столбцы. `comm` показывает имя программы, `args` — командную строку. `ps` без аргументов показал Bash и сам кратковременный процесс `ps`. `pts/1` — псевдотерминал сеанса.

`sleep 60 &` запускает внешний процесс на 60 секунд. `&` возвращает приглашение Bash сразу, пока процесс работает. Без `&` Bash ждёт его завершения. Два одинаковых запуска можно различить через `ps -C sleep -o pid,args`, где `-C` отбирает по имени. `echo "$!"` печатает PID последней фоновой команды этой оболочки. Встроенный `cd` меняет каталог в самом Bash.

| Команда | Что читать в выводе |
| --- | --- |
| `free -h` | Оперативная память. На VM было 913 МиБ всего, 480 МиБ полностью свободно и около 617 МиБ доступно с учётом освобождаемого кэша. `Swap: 0B` — подкачка не настроена. |
| `df -h /` | Место в файловой системе корня. Было 8,0 ГиБ всего, 1,6 ГиБ занято, 6,4 ГиБ доступно, заполнение 20%. |
| `du -sh ~` | Суммарное место, занятое домашним каталогом. `-s` даёт одну строку, `-h` делает размеры читаемыми. |
| `lsblk` | Дерево дисков, разделов и точек монтирования. `/dev/nvme0n1p1` — специальный файл первого раздела (`p1`) устройства `nvme0n1`. На VM этот раздел смонтирован в `/`. |

## 5. Go и сборка API

`command -v go` ничего не вывел: Bash не нашёл `go` в каталогах из `PATH`. `dnf info golang` показал доступный пакет Go 1.26.10. Проект требует минимум Go 1.24 в `app/go.mod`. Установили Go командой `sudo dnf install golang` под `ec2-user`, а под `learner` проверили `go version`. В выводе `linux/amd64` обозначает ОС и архитектуру.

На VM под `learner` создали `mkdir -p ~/tickets/app`. Флаг `-p` создаёт отсутствующие родительские каталоги. С Mac из папки проекта `app` перенесли нужные файлы:

```bash
scp -r go.mod go.sum api internal learner@<IP_VM>:/home/learner/tickets/app/
```

`scp` копирует по SSH, `-r` переносит каталоги с вложениями. После двоеточия указан путь на VM. В `go.mod` описан модуль и зависимости, `go.sum` содержит контрольные суммы. Проверили файлы через `ls ~/tickets/app`, затем на VM выполнили:

```bash
cd ~/tickets/app
go build -o tickets-api ./api
ls -lh tickets-api
HTTP_ADDR=127.0.0.1:8080 ./tickets-api
```

`go build` компилирует пакет из `./api`, а `-o` задаёт имя исполняемого файла. `ls -lh` показывает размер и право запуска `x`. Сборка создаёт файл, запуск создаёт процесс. `./` указывает на файл в текущем каталоге. Присваивание перед командой передаёт переменную только запускаемой программе. При первом запуске получили `DATABASE_URL is required`: API требует настройки базы до открытия HTTP-порта.

## 6. PostgreSQL и проверка входа

`command -v psql` ничего не вывел. `dnf list --available 'postgresql*-server'` показал серверные пакеты версий 15–18. Кавычки передали шаблон со звёздочкой в `dnf`, чтобы его не раскрыл Bash. Выбрали PostgreSQL 16.15.

Под `ec2-user` выполнили:

```bash
sudo dnf install postgresql16-server
sudo postgresql-setup --initdb
sudo systemctl start postgresql
systemctl status postgresql --no-pager
sudo -u postgres psql
```

- Установка добавила программы, а `--initdb` один раз создал начальные данные в `/var/lib/pgsql/data`.
- `systemctl start` запускает службу сейчас. `status` показывает её состояние, PID и журнал. `--no-pager` печатает вывод прямо в терминал. `ExecStartPre` в выводе был успешно завершившейся проверкой каталога данных.
- `sudo -u postgres` запускает клиент `psql` от имени пользователя Linux `postgres`. Клиент по умолчанию подключился локально к базе `postgres` под одноимённой ролью PostgreSQL.

В приглашении `postgres=#` выполнили:

```sql
SELECT current_user, current_database();
CREATE ROLE tickets_app LOGIN;
```

Первый запрос показывает текущую роль и базу. `CREATE ROLE … LOGIN` создаёт учётную запись PostgreSQL с правом подключения. Задали пароль командой клиента `\password tickets_app`, которая запрашивает его дважды со скрытым вводом. Затем выполнили `CREATE DATABASE tickets OWNER tickets_app;`, чтобы роль могла создавать таблицы в своей базе. `\q` закрывает клиент, а сервер продолжает работать.

Проверили вход теми же учётными данными, что нужны API:

```bash
psql -h 127.0.0.1 -U tickets_app -d tickets -W
```

`-h` выбирает адрес и подключение по TCP, `-U` задаёт роль, `-d` — базу, `-W` заранее запрашивает пароль. Получили `Ident authentication failed`. Клиент дошёл до PostgreSQL на порту 5432, но сервер выбрал метод `ident`, который проверяет имя пользователя ОС. Запрос пароля от клиента не меняет выбор метода сервером.

Посмотрели порядок правил:

```bash
sudo -u postgres psql -c 'SELECT line_number, type, database, user_name, address, auth_method FROM pg_hba_file_rules ORDER BY line_number;'
```

`-c` выполняет один запрос и возвращает в Bash. PostgreSQL использует первое совпавшее правило из `pg_hba.conf`. Сначала мы заменили метод у общего правила `all all`. Запрос показал, что пароль потребовался бы всем локальным клиентам по IPv4. Исправили область действия, отредактировав файл через `sudo nano /var/lib/pgsql/data/pg_hba.conf`:

```text
host    tickets    tickets_app    127.0.0.1/32    scram-sha-256
host    all        all            127.0.0.1/32    ident
```

`host` — подключение по TCP, `/32` ограничивает совпадение одним IPv4-адресом. Первая строка включает проверку пароля для конкретной базы и роли. Отдельное правило `local … peer` продолжает обслуживать соединения через локальный сокет. После проверки порядка строк через `pg_hba_file_rules` выполнили `sudo systemctl reload postgresql`. `reload` попросил PostgreSQL перечитать настройки без перезапуска. Повторный вход по TCP удался, а `SELECT current_user, current_database();` вернул `tickets_app | tickets`.

## 7. Ручной запуск и HTTP-проверки

Из каталога `~/tickets/app` под `learner` ввели пароль через `read -r -s -p 'Пароль PostgreSQL: ' db_password`. `-s` скрывает ввод, `-p` выводит приглашение, `-r` сохраняет обратные косые черты. Запустили API так:

```bash
PGPASSWORD="$db_password" \
DATABASE_URL='postgres://tickets_app@127.0.0.1:5432/tickets?sslmode=disable' \
HTTP_ADDR=127.0.0.1:8080 \
./tickets-api
```

`DATABASE_URL` задаёт роль, адрес, порт и базу. `PGPASSWORD` передаёт пароль отдельно. `sslmode=disable` относится к соединению с PostgreSQL на той же VM. `HTTP_ADDR` задаёт другую сторону: где API принимает запросы. `127.0.0.1` указывает на саму машину, с которой выполняется соединение. Когда API написал `api listening`, оставили его в первом SSH-сеансе и открыли второй для запросов:

| Команда | Результат |
| --- | --- |
| `curl -i http://127.0.0.1:8080/health` | API отвечает: `{"status":"ok"}`. |
| `curl -i http://127.0.0.1:8080/ready` | API проверяет соединение с БД: `{"status":"ready"}`. |
| `curl -i http://127.0.0.1:8080/api/events` | API читает каталог через SQL. Сначала получили `200 OK` и `[]`. |

`curl` использует GET по умолчанию. `-i` добавляет HTTP-статус и заголовки к телу ответа. `200 OK` с пустым массивом — успешный запрос без видимых записей. По коду API показывает только будущие события. SQL-запрос `SELECT id, starts_at, starts_at > now() AS upcoming FROM events ORDER BY starts_at;` помог проверить, что таблица была пустой.

Для загрузки демоданных перезапустили API с дополнительной строкой `SEED_DEMO=true \` перед `./tickets-api`. При диагностике предложили найти процесс через `ps -C tickets-api -o pid,args` и проверить точное значение через `grep -z -x -c 'SEED_DEMO=true' /proc/<PID>/environ`. `-z` учитывает нулевые разделители, `-x` ищет всю запись, `-c` печатает число совпадений и не выводит пароль. Конкретная причина первого неудачного запуска с демоданными не зафиксирована. В итоге каталог вернул четыре записи: `night-jazz`, `city-layers`, `print-studio` и `last-seat`.

```bash
ss -ltnp 'sport = :8080'
```

`ss` показывает сокеты. `-l` оставляет слушающие, `-t` — TCP, `-n` показывает числа, `-p` выводит процесс. Выражение фильтрует локальный порт. Увидели `LISTEN` на `127.0.0.1:8080`, `pid=58791` и `fd=6`. PID обозначает процесс, FD — номер открытого сокета внутри него. `Peer Address:Port` со значением `0.0.0.0:*` означает, что у слушающего сокета нет конкретного клиента. **Ctrl+C** в первом сеансе останавливает ручной процесс, после чего его сокет закрывается.

## 8. Служба systemd, журнал и перезагрузка

Под `ec2-user` создали `/etc/systemd/system/tickets-api.service`. После добавления автозапуска он выглядел так:

```ini
[Unit]
Description=Tickets API
Wants=postgresql.service
After=postgresql.service

[Service]
User=learner
WorkingDirectory=/home/learner/tickets/app
Environment=HTTP_ADDR=127.0.0.1:8080
Environment="DATABASE_URL=postgres://tickets_app@127.0.0.1:5432/tickets?sslmode=disable"
EnvironmentFile=/etc/tickets-api.env
ExecStart=/home/learner/tickets/app/tickets-api

[Install]
WantedBy=multi-user.target
```

`Wants` просит запустить PostgreSQL вместе с API, `After` задаёт порядок. `User` задаёт пользователя процесса, `WorkingDirectory` — текущую папку, `ExecStart` — команду запуска. `Environment` передаёт параметры, `EnvironmentFile` указывает на отдельный файл с паролем. `WantedBy` привязывает включённую службу к обычной загрузке системы.

`sudo install -m 600 /dev/null /etc/tickets-api.env` создал пустой файл, доступный владельцу `root`. Повтор команды очистит файл. Через `sudo nano` записали `PGPASSWORD='ТВОЙ_ПАРОЛЬ'`. Такой формат подходит для пароля без одинарных кавычек. Проверка `sudo ls -l /etc/tickets-api.env` должна показать `-rw-------` и владельца `root`. Настоящий пароль в проекте и выводах команд не храним.

| Команда | Назначение |
| --- | --- |
| `sudo systemctl daemon-reload` | Перечитать файлы описаний служб systemd. Отличается от `systemctl reload postgresql`, который просит само приложение перечитать его настройки. |
| `sudo systemctl start tickets-api` | Запустить API сейчас. Первый PID службы был `60295`. |
| `systemctl status tickets-api --no-pager` | Проверить `Active`, `Main PID` и последние сообщения. |
| `sudo journalctl -u tickets-api.service -n 10 --no-pager` | Показать до десяти последних записей выбранной службы. `-u` задаёт службу, `-n` количество. |
| `sudo systemctl restart tickets-api.service` | Остановить текущий процесс и запустить новый. В журнале были `Stopping`, `Deactivated successfully`, `Started` и `api listening` с новым PID `60513`. |
| `sudo systemctl enable tickets-api.service` | Настроить автозапуск, создав ссылку на службу для цели загрузки. |
| `systemctl is-enabled tickets-api.service` | Проверить настройку автозапуска. |
| `sudo systemctl reboot` | Перезагрузить VM. SSH отсоединяется, после загрузки нужно подключиться снова. |
| `systemctl is-active postgresql.service tickets-api.service` | Проверить текущее состояние обеих служб. После перезагрузки получили две строки `active`. |

В журнале `systemd[1]` сообщил о старте службы, а `tickets-api[60295]` — об открытии порта. Число в скобках помогает привязать запись к конкретному запуску. Причина разобранного перезапуска известна: мы вызвали `systemctl restart`. После перезагрузки запрос `curl -i http://127.0.0.1:8080/ready` снова вернул `200 OK` и `{"status":"ready"}`. На этом первый этап завершён. Следующая неделя начинается с Nginx перед API.
