# Неделя 2. Сеть, Nginx и диагностика запроса

На той же VM добавили Nginx перед API, проверили DNS и TLS, воспроизвели отказ TCP и два разных тайм-аута. После восстановления итоговый HTTPS-запрос к `/ready` вернул `200 OK` и `{"status":"ready"}`. Все HTTP-проверки выполняли внутри SSH-сеанса. Исходный стенд описан в [конспекте первой недели](week-01-linux.md).

## 1. Nginx и два соединения

Проверили наличие пакета через `dnf list --installed nginx`. После сообщения `No matching Packages to list` установили пакет под `ec2-user` через `sudo dnf install nginx`. `nginx -v` показал установленную версию `1.30.6`.

```bash
sudo nginx -T | grep -nE '^[[:space:]]*(listen|include)[[:space:]]'
```

`-T` проверяет и печатает полную конфигурацию. Конвейер `|` передаёт стандартный вывод в `grep`. Флаг `-n` выводит номера строк в объединённом выводе, `-E` включает расширенные регулярные выражения. Шаблон ищет `listen` и `include` в начале строки после возможных пробелов.

Основной файл `/etc/nginx/nginx.conf` подключает `/etc/nginx/conf.d/*.conf` через `include`. Один экземпляр Nginx применяет оба файла. В стандартном блоке оставили локальные слушатели `127.0.0.1:80` и `[::1]:80`. Через `sudo nano /etc/nginx/conf.d/tickets.conf` создали отдельный блок приложения:

```nginx
server {
    listen 127.0.0.1:8081;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
```

`listen` задаёт адрес и порт входящего соединения. `location /` охватывает все пути, а `proxy_pass` пересылает запрос API, сохраняя путь. Из nano сохраняли через **Ctrl+O**, **Enter**, затем выходили через **Ctrl+X**. `sudo nginx -t` проверяет конфигурацию без печати всех файлов. После успешной проверки запустили службу через `sudo systemctl start nginx`. После дальнейших изменений использовали `sudo nginx -t && sudo systemctl reload nginx`. Оператор `&&` запускает перечитывание только после успешной проверки.

| URL на VM | Кто принимает запрос |
| --- | --- |
| `http://127.0.0.1/` | Стандартный сайт Nginx на порту 80 по умолчанию. |
| `http://127.0.0.1:8080/ready` | API напрямую. |
| `http://127.0.0.1:8081/ready` | Nginx, который по отдельному TCP-соединению передаёт запрос API на порт 8080. |

В двух последних случаях `curl -i` показал одинаковое тело `{"status":"ready"}`, потому что запрос обрабатывает один API. У ответа через прокси был заголовок `Server: nginx/1.30.6`. `-i` добавляет HTTP-статус и заголовки к телу ответа. `ss -ltnp 'sport = :8080'` из первой недели позволяет проверить, кто слушает порт. Для проверки другого порта достаточно изменить число в фильтре.

## 2. Отказ соединения и HTTP 502

Через `sudo systemctl stop tickets-api.service` остановили только API. Прямой запрос на `8080` получил отказ TCP-соединения без HTTP-статуса. Запрос на `8081` дошёл до работающего Nginx, который вернул `502 Bad Gateway`. После `sudo systemctl start tickets-api.service` прокси снова вернул `200 OK`.

`sudo tail -n 10 /var/log/nginx/error.log` показал последние десять строк журнала ошибок. В записи о 502 были `connect() failed (111: Connection refused) while connecting to upstream`, `host: "127.0.0.1:8081"` и `upstream: "http://127.0.0.1:8080/ready"`. Поле `host` показывает имя или адрес из HTTP-запроса клиента, а `upstream` — куда Nginx отправлял запрос. `journalctl -u tickets-api.service` из первой недели помогает сопоставить ошибку прокси с остановкой или запуском API.

## 3. DNS и адрес подключения

```bash
curl --noproxy '*' -i http://tickets.invalid:8081/ready
dig tickets.invalid A
curl --noproxy '*' --resolve 'tickets.invalid:8081:127.0.0.1' \
  -i http://tickets.invalid:8081/ready
```

- DNS сопоставляет имя с адресом. `dig` отправляет отдельный DNS-запрос. `A` запрашивает IPv4-адрес, `AAAA` используется для IPv6. Номер HTTP-порта указывать в таком запросе не нужно.
- `tickets.invalid` выбрали для эксперимента с несуществующим именем. `dig` получил ответ с `status: NXDOMAIN`: запрос дошёл до DNS, сервер ответил, что имени нет. `QUERY: 1, ANSWER: 0` означает один вопрос и отсутствие записей в секции ответа.
- Без адреса первый `curl` завершился с кодом `6` и `Could not resolve host`. TCP и HTTP в этом случае ещё не начались.
- `--noproxy '*'` исключает прокси из окружения. `--resolve` подставляет IP для указанной пары имя–порт только в этом запуске. Имя остаётся в URL и заголовке `Host`. С подстановкой запрос получил `200 OK`.

## 4. HTTPS и TLS

TLS шифрует трафик, защищает его от изменения и позволяет клиенту проверить подлинность сервера. В нашем стенде TLS заканчивается на Nginx. Клиент соединяется с ним по HTTPS, а Nginx передаёт запрос API по локальному HTTP.

```bash
sudo openssl req -x509 -newkey rsa:2048 -noenc -days 7 \
  -subj '/CN=tickets.invalid' \
  -addext 'subjectAltName=DNS:tickets.invalid' \
  -keyout /etc/nginx/tickets-lab.key \
  -out /etc/nginx/tickets-lab.crt
```

`req -x509` создаёт самоподписанный сертификат, `-newkey rsa:2048` — новый RSA-ключ. `-noenc` сохраняет закрытый ключ без парольной фразы, чтобы Nginx мог запуститься без ручного ввода. `-days 7` задаёт срок, `-subj` задаёт поля субъекта, а `-addext` добавляет имя для проверки в расширении SAN. Закрытый ключ пишется в `.key` и остаётся на сервере, сертификат пишется в `.crt` и передаётся клиенту. `openssl x509 -in /etc/nginx/tickets-lab.crt -noout -dates -ext subjectAltName` показывает даты и имя без печати всего сертификата.

В тот же блок `server` добавили:

```nginx
listen 127.0.0.1:8443 ssl;
server_name tickets.invalid;

ssl_certificate     /etc/nginx/tickets-lab.crt;
ssl_certificate_key /etc/nginx/tickets-lab.key;
```

`ssl` включает TLS на порту 8443, а `server_name` задаёт имя сайта. Слушатель HTTP на 8081 и `proxy_pass` остались в блоке. Проверили конфигурацию и перечитали её.

```bash
curl --noproxy '*' --resolve 'tickets.invalid:8443:127.0.0.1' \
  --cacert /etc/nginx/tickets-lab.crt \
  -i https://tickets.invalid:8443/ready
```

Без `--cacert` клиент не доверяет самоподписанному сертификату. С этим флагом `curl` доверяет нашему сертификату для данного запуска и проверяет срок и имя из URL. Только затем отправляет HTTP-запрос. `--resolve` выбирает IP, а проверка имени по-прежнему использует `tickets.invalid`.

Отдельно посмотрели согласование TLS:

```bash
openssl s_client -connect 127.0.0.1:8443 \
  -servername tickets.invalid -verify_hostname tickets.invalid \
  -CAfile /etc/nginx/tickets-lab.crt -verify_return_error -brief </dev/null
```

`-connect` выбирает адрес и порт. `-servername` передаёт имя серверу через SNI для выбора сертификата. `-verify_hostname` проверяет имя у клиента. `-CAfile` задаёт доверенный сертификат, `-verify_return_error` завершает соединение при ошибке проверки, `-brief` сокращает вывод. `</dev/null` даёт пустой ввод вместо ожидания текста с клавиатуры.

Увидели `TLSv1.3`, `TLS_AES_256_GCM_SHA384`, `Verification: OK` и `Verified peername: tickets.invalid`. AES-GCM защищает трафик, SHA-384 участвует в выработке ключей, RSA-подпись доказывает владение ключом сертификата, а временный обмен X25519 помогает получить общий секрет для соединения.

## 5. Интерфейсы и маршруты

| Команда | Наблюдение |
| --- | --- |
| `ip route get 127.0.0.1` | `local … dev lo src 127.0.0.1`: трафик адресован самой VM и идёт через loopback. |
| `ip route get 1.1.1.1` | `via 172.31.32.1 dev ens5 src 172.31.42.177`: трафик пошёл бы через шлюз, используя частный IP VM. |
| `ip -br addr` | Краткий список интерфейсов: `lo` с `127.0.0.1/8` и `::1/128`, `ens5` с `172.31.42.177/20`. |

`ip route get` спрашивает ядро, какой маршрут оно выбрало бы, без отправки пакетов. `via` показывает следующий узел, `dev` — интерфейс, `src` — исходный адрес. `-br` означает краткий вывод, а суффикс после `/` задаёт длину сетевого префикса в битах.

## 6. Тайм-аут клиента и HTTP 504

```bash
sudo systemctl kill --signal=STOP tickets-api.service
curl -v --max-time 3 http://127.0.0.1:8080/ready
sudo systemctl kill --signal=CONT tickets-api.service
curl -i http://127.0.0.1:8080/ready
```

`STOP` приостановил процесс с сохранением PID и открытого сокета. `curl -v` показал установленное TCP-соединение и отправленный GET, но за три секунды (`--max-time 3`) не получил ни байта. Код `28` — тайм-аут клиента. `CONT` возобновил работу того же процесса, и запрос снова вернул `200 OK`.

Затем временно добавили `proxy_read_timeout 2s;` в `location /` и перечитали конфигурацию Nginx. Эта директива ограничивает паузу между чтениями ответа от API. Повторили `STOP` и `CONT`, отправляя `curl -i --max-time 5 http://127.0.0.1:8081/ready`. У прокси лимит был короче, поэтому клиент получил HTTP `504 Gateway Time-out`. После `CONT` тот же запрос вернул `200 OK`.

В журнале Nginx было `upstream timed out (110: Connection timed out) while reading response header from upstream`. При 502 отказ произошёл `while connecting to upstream`. При 504 соединение было открыто, а сбой произошёл в ожидании заголовков. Убрали учебный лимит и подтвердили работу итоговым HTTPS-запросом к `/ready`.

| Симптом | Где искать |
| --- | --- |
| `Could not resolve host` | Разрешение имени. Сравнить DNS-ответ `dig` и запрос с `--resolve`. |
| `Connection refused` | Входящее TCP-соединение. Проверить порт через `ss` и состояние службы через `systemctl`. |
| Ошибка сертификата | TLS. Проверить имя, срок и доверие через `openssl s_client` и `openssl x509`. |
| `502` в нашем опыте | Nginx ответил, но не смог подключиться к API. Проверить лог и прямой запрос на 8080. |
| `curl: (28)` в нашем опыте | Прямое подключение прошло, клиент не дождался HTTP-ответа. Сверить этапы через `curl -v`. |
| `504` в нашем опыте | Nginx подключился к API и не дождался заголовков. Проверить лог прокси и состояние API. |

Если сбой сопровождается подозрением на нехватку места, `df -h /` показывает свободное место в корневой файловой системе, а `du -sh КАТАЛОГ` — сколько места занимает конкретный каталог. Обе команды разобраны в первой неделе.
