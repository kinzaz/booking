# Неделя 3. Git, smoke-тест и восстановление API

В этой неделе подготовили проект к хранению в Git, проверили сценарий бронирования через Nginx и восстановили службу API по [инструкции для Amazon Linux](../runbooks/amazon-linux-vm.md). Развёртывание с нуля на отдельной VM не проводили.

## 1. Локальный репозиторий

На Mac в папке проекта выполнили `git init`. Команда создаёт служебный каталог `.git` с настройками и будущей историей проекта.

| Команда | Что показывает или меняет |
| --- | --- |
| `git status --short --ignored` | Короткий статус. `??` обозначает неотслеживаемый путь, `!!` — игнорируемый. |
| `git status --short --untracked-files=all` | Раскрывает отдельные файлы внутри неотслеживаемых каталогов. |
| `git add -- .gitignore README.md app/ deploy/ docs/ infra/ load/ roadmap.md` | Помещает выбранные версии файлов в индекс. `--` отделяет параметры от путей. |
| `git diff --cached --stat` | Показывает сводку изменений, подготовленных к коммиту. |
| `git commit -m "Initial commit: ticket booking app and lab notes"` | Сохраняет индекс в локальной истории с указанным сообщением. |
| `git log -1 --oneline` | Показывает последний коммит одной строкой. |

Перед первым коммитом индекс содержал 32 файла и 2675 добавленных строк. `.idea/`, `app/frontend/dist/` и `app/frontend/node_modules/` были исключены через `.gitignore`. В выводе со списком файлов не было путей к файлам с паролями или ключами. Вывод `git log` после коммита не зафиксирован.

## 2. Миграции, демоданные и smoke-тест

API при старте применяет SQL-миграции из `app/internal/booking/migrations/` и отмечает применённые файлы в таблице `schema_migrations`. `SEED_DEMO=true` дополнительно загружает мероприятия из `seed.sql`. Smoke-тесту нужно будущее мероприятие `night-jazz` со свободным местом. Повторная загрузка демоданных сохраняет уже существующие записи, включая их даты.

С Mac скопировали `deploy/smoke.sh` через `scp` в `/home/learner/tickets/smoke.sh`. Под `learner` на VM запустили:

```bash
BASE_URL=http://127.0.0.1:8081 bash ~/tickets/smoke.sh
```

`BASE_URL` передаёт скрипту адрес Nginx на время запуска. Bash читает команды из файла. `curl -fsS` завершает запрос с ошибкой при статусе HTTP 400 и выше, убирает индикатор прогресса и сохраняет сообщения об ошибках. Python разбирает JSON. Конвейер `|` передаёт результат одной команды следующей, а `$(...)` подставляет вывод выполненной команды в присваивание или сравнение.

Скрипт проверяет `/ready`, создаёт бронь с новым случайным `Idempotency-Key`, повторяет запрос и сравнивает ID. Затем читает бронь в статусе `active`, отменяет её и проверяет `cancelled`. Повтор исходного запроса после отмены всё равно должен вернуть тот же ID. После извлечения ID обработчик `trap ... EXIT` даёт скрипту возможность попытаться отменить бронь при досрочном выходе.

## 3. Восстановление службы по инструкции

Перед упражнением smoke-тест прошёл. Под `ec2-user` выполнили:

```bash
sudo systemctl disable --now tickets-api.service
sudo mv -i /etc/systemd/system/tickets-api.service /root/tickets-api.service.week03.bak
sudo systemctl daemon-reload
```

`disable --now` отключает автозапуск и останавливает службу. `mv -i` переносит файл в резервное место и спрашивает подтверждение перед перезаписью. `daemon-reload` перечитывает описания служб. После этого `systemctl status tickets-api.service --no-pager` сообщил `Unit tickets-api.service could not be found`, а `curl -i http://127.0.0.1:8081/ready` через Nginx вернул `502 Bad Gateway`.

Воссоздали файл службы по runbook, перечитали настройки и вернули запуск через `sudo systemctl enable --now tickets-api.service`. Для упражнения сохранили бинарный файл, конфигурацию Nginx, файл окружения и базу с данными. Это проверка восстановления описания службы на существующей VM.

Первая попытка запуска теста под `ec2-user` завершилась `No such file or directory`: оболочка раскрыла `~` в `/home/ec2-user`, а скрипт лежал в `/home/learner`. При доступе по полному пути также нужны права прохода по родительским каталогам и чтения файла. Повтор под `learner` прошёл:

```text
Smoke test passed: 74e33288-43f7-423f-a9b3-303798b5f2e6
```

Этот результат подтвердил восстановление всего пути запроса через Nginx, API и PostgreSQL, включая создание и отмену брони.

## 4. Новая миграция на существующей базе

В `schema_migrations` изначально была только `001_init.sql`. Добавили отдельный файл `002_add_event_organizer.sql`:

```sql
ALTER TABLE events
    ADD COLUMN organizer_name text;
```

Столбец допускает `NULL`, поэтому существующие записи сохраняются без заполнения нового поля. Уже применённую миграцию оставили как есть: API отслеживает применённые файлы по имени.

Скопировали SQL на VM через `scp`. Под `learner` собрали `go build -o tickets-api.next ./api`, сохранили предыдущий бинарник через `cp -p tickets-api tickets-api.before-002` и поставили новый на путь службы через `mv tickets-api.next tickets-api`. SQL встраивается при сборке и выполняется при запуске API. Команду `sudo systemctl restart tickets-api.service` выполнили под `ec2-user`.

После запуска запросы к `schema_migrations` и `information_schema.columns` показали две миграции (`001_init.sql` и `002_add_event_organizer.sql`) и столбец `organizer_name | text | YES`. Повторный запуск той же версии прошёл smoke-тест через Nginx. Это подтвердило, что API пропустил уже применённый `ADD COLUMN` и что сценарий бронирования продолжил работать.

```text
Smoke test passed: 93952584-5467-45ca-a8ce-16ae1ef8b60f
```
