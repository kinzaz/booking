# Неделя 7. От pull request до проверенного образа в Amazon ECR

Практика 21 ноября 2026 года, проект бронирования билетов. Начальная точка — работающий Compose-стенд и скрипт проверки бронирования. Конечная точка — образ API в приватном реестре AWS, который можно скачать по точному идентификатору. Развёртывание этого образа на сервере относится к неделе 8.

Как читать результат. В GitHub мы открываем коммит и узнаём, какой код попал в сборку. В ECR открываем тег с тем же значением и находим digest. Для развёртывания передаём ссылку с digest. Если позже появится другая сборка, эта ссылка по-прежнему обозначает прежнее содержимое, пока оно хранится в реестре.

Основные файлы: [workflow](../../.github/workflows/pr-ci.yml), [Dockerfile API и worker](../../app/Dockerfile), [Compose](../../deploy/compose.yaml), [smoke-тест](../../deploy/smoke.sh), [код миграций](../../app/internal/booking/store.go). При чтении workflow полезно держать рядом следующие две схемы.

**Путь образа**

```text
GitHub, коммит в master
  → runner задания check собирает образ и запускает из него контейнер API
  → smoke-тест проходит через Nginx; отдельно проверяется обновление базы
  → docker save сохраняет образ контейнера API в api.tar
  → GitHub временно хранит архив как artifact с именем tested-api
  → другой runner, задание publish, скачивает архив и выполняет docker load
  → docker tag добавляет адрес ECR; docker push передаёт образ в tickets-api
  → ECR возвращает digest; он попадает в Summary запуска
```

**Путь доступа** идёт параллельно. По нему передаются удостоверения и запросы на разрешение, сам образ движется по схеме выше.

```text
GitHub выдаёт заданию publish подписанный OIDC-токен
  → задание предъявляет токен AWS STS и указывает желаемую IAM-роль
  → AWS проверяет издателя токена и условия доверия роли
  → STS выдаёт временные учётные данные сессии роли
  → AWS CLI с этими данными запрашивает пароль для входа в ECR
  → Docker входит в реестр и загружает образ в пределах прав роли
```

## 2. Что проверял CI и почему он запускался дважды

CI (continuous integration) — автоматические проверки изменений в общем репозитории. Workflow — файл с событиями запуска и заданиями. Job — задание на runner, то есть машине, исполняющей команды. Steps одного задания используют одну машину. У двух заданий с `runs-on: ubuntu-latest` отдельные машины, поэтому локальные образы Docker и файлы между ними нужно передавать явно.

| Событие | Как ведёт себя этот workflow | Зачем |
|---|---|---|
| Открыли или обновили pull request | Запускается `check`; `publish` получает Skipped | До решения о слиянии узнать, собирается ли код и работает ли бронирование |
| Слияние создало push в `master` | Новый `check`; после успеха запускается `publish` | Проверить и опубликовать результат, фактически попавший в основную ветку |
| Проверка на `master` провалилась | Зависимое задание публикации пропускается | В реестр не должен попасть новый образ из неудавшейся проверки |

Условия записаны в разных местах и отвечают на разные вопросы. `on` определяет, когда GitHub создаст запуск. `needs: check` в задании публикации задаёт зависимость от успешной проверки. `if` в этом задании требует событие push и ссылку `refs/heads/master`. Любой разрешённый push в эту ветку подходит под условие, включая прямой push. Правило «все изменения только через PR» потребовало бы отдельной настройки ветки.

В учебной ветке коммит `a91b4f0` добавил публикацию. В результате слияния появился `dd3a551…`. При событии push переменная `GITHUB_SHA` в этом запуске содержит полный SHA коммита в master. Именно поэтому в ECR видим тег `dd3a551…`. При событии pull_request значение обычно указывает на подготовленный GitHub коммит пробного слияния. Для SHA исходной ветки PR существует отдельное поле `github.event.pull_request.head.sha`.

### Что делает check

1. `actions/checkout` загружает исходники выбранной ревизии. `actions/setup-go` читает версию Go из `app/go.mod`. Команды Go запускаются в `app`, где лежит файл модуля.
2. `go build ./...` проверяет компиляцию пакетов. Запущенного HTTP-сервера после этой команды нет. `go test ./...` запускает тесты пакетов. В учебном проекте вывод был `[no test files]`: успешный код возврата здесь говорит о возможности обработать пакеты, а поведение бронирования проверяется отдельным шагом.
3. `docker compose -f deploy/compose.yaml up -d --build --wait frontend` собирает и поднимает frontend вместе с его зависимостями. PostgreSQL проходит healthcheck, API получает подключение к базе, применяет миграции и становится готов, после чего стартует frontend с Nginx. Наружу опубликован порт frontend. Путь запроса — runner → localhost:8080 → Nginx → API → PostgreSQL.
4. `bash deploy/smoke.sh` обращается к реальному HTTP-сервису. Сначала запрашивает `/ready`, затем создаёт бронь на одно место для `night-jazz`. Скрипт повторяет запрос с тем же `Idempotency-Key` и требует получить прежний ID. Читает статус `active`, отменяет бронь, проверяет `cancelled`, снова повторяет запрос с исходным ключом и проверяет тот же ID. Идемпотентность здесь означает, что повтор одной операции с тем же ключом не создаёт вторую бронь. Новый запуск скрипта генерирует свой ключ.
5. Второй Compose-проект `tickets-upgrade` поднимает отдельную базу. В неё загружается SQL версии 001, в таблицу истории вносится имя миграции и добавляется мероприятие с 7 доступными местами из 10. Затем запускается текущий API. Это воспроизводит обновление системы, у которой уже есть схема и пользовательские данные.
6. Первое SQL-утверждение требует одну запись `002_add_event_organizer.sql` в истории. Второе требует, чтобы у прежнего мероприятия сохранились 7 мест, а новое поле `organizer_name` имело значение NULL. Так проверяются и доступность нового столбца, и чтение прежней строки. При падении одного из шагов workflow выводит логи обоих стендов.

Почему нужны две базы? На чистой базе могли успешно выполниться обе миграции подряд. Это ещё не воспроизводит положение пользователя, который сохранил данные до обновления. Например, новый обязательный столбец без подходящего значения для старых строк может успешно добавиться в пустую таблицу и вызвать ошибку на заполненной. Код проекта использует транзакцию, сверяет имена с историей миграций и берёт транзакционную advisory-блокировку PostgreSQL, чтобы параллельные старты приложения не применили одну миграцию одновременно.

## 3. Что такое SHA коммита

Хеш-функция вычисляет из входных байтов значение фиксированной длины. Одинаковый вход и алгоритм дают один результат. Идентификатор коммита Git вычисляется для объекта коммита. В этом репозитории он отображается 40 шестнадцатеричными символами (SHA-1). Сокращения вроде `dd3a551` удобны в переписке, если Git может однозначно определить объект. В тег образа мы записали все 40 символов.

Что входит в объект коммита? Ссылка на дерево файлов, ссылки на родителей, автор, коммитер, даты и сообщение. Поэтому одинаковое состояние файлов может встретиться в двух коммитах с разными SHA. Например, изменение сообщения через amend создаёт новый объект. Коммит слияния содержит ссылки на родителей. Имя ветки в идентификатор не входит. Ветка — подвижная ссылка, и после следующего слияния `master` будет указывать дальше, а `dd3a551…` по-прежнему обозначит тот же коммит.

Прочитать эти значения локально можно без переключения ветки. Для последней команды объект должен быть загружен в локальный репозиторий.

```bash
git branch --show-current
git rev-parse HEAD
git show --no-patch --format=fuller dd3a551a01f33d6a2c82bceb50b0798a0885c895
```

Для учебной локальной сборки мы использовали такую связь:

```bash
commit=$(git rev-parse HEAD)
docker build --target api \
  --label "org.opencontainers.image.revision=$commit" \
  --tag "tickets-api:$commit" ./app
docker image inspect "tickets-api:$commit" \
  --format '{{ index .Config.Labels "org.opencontainers.image.revision" }}'
```

Здесь `--target api` выбирает стадию API из многостадийного Dockerfile. Последней описана стадия worker. Тег — внешнее имя для поиска образа. Label — запись внутри конфигурации образа. Команда inspect читает label. Локальная сборка берёт файлы из рабочей директории, включая незакоммиченные изменения в контексте сборки. Поэтому сама надпись с Git SHA ещё не доказывает соответствие исходников. В CI основание для этой связи даёт checkout конкретного коммита и ход сборки. В фактическом CI связь записана в **теге и Summary**; workflow не добавляет показанный в локальном упражнении label.

## 4. Что такое digest и почему им закрепляют релиз

Docker-образ включает слои файловой системы и конфигурацию запуска. **Манифест** связывает конфигурацию и слои ссылками с их digest. **Индекс образа** — документ уровнем выше, он содержит ссылки на манифесты. Индекс может объединять варианты под разные платформы. По одной строке Image Index нельзя определить, для скольких платформ собрали образ. [Спецификация OCI Image Index](https://github.com/opencontainers/image-spec/blob/main/image-index.md)

У каждого объекта может быть собственный digest. В записи `sha256:c839…` до двоеточия указан алгоритм, после него — 64 шестнадцатеричных символа, представляющих 256 бит результата. В нашей карточке ECR **Artifact type = Image Index**. Следовательно, опубликованное верхнеуровневое значение идентифицирует байты индекса. Индекс ссылается по digest на дочерние объекты. Это позволяет зафиксировать целую структуру, хотя Docker не вычисляет наш опубликованный digest простым хешированием каталога приложения.

| Значение | Что оно обозначает | Где встретилось |
|---|---|---|
| Git SHA | Объект коммита и через его дерево версию исходников | Git, `GITHUB_SHA` |
| Имя тега в ECR | Присвоенное издателем имя для поиска | После `tickets-api:` |
| Image ID из `docker inspect` для контейнера | Идентификатор локального образа, использованного для контейнера | Выражение `{{.Image}}` в задании check |
| Digest индекса в ECR | Конкретный опубликованный индекс образа | После `tickets-api@`, в логе push и на странице Details |
| ID контейнера | Экземпляр, созданный при запуске образа | `docker compose ps -q api` |
| Хеш файла `api.tar`, если его вычислить | Байты транспортного архива | При проверке файла; в упражнении не использовался |

**Две формы адреса одного опубликованного результата**

```text
998115851061.dkr.ecr.eu-north-1.amazonaws.com/tickets-api:dd3a551a01f33d6a2c82bceb50b0798a0885c895
998115851061.dkr.ecr.eu-north-1.amazonaws.com/tickets-api@sha256:c839290f85a9f1dbbc7e2e9887b50ff5fae8f0245cb2280654605125152cff83
```

В первом случае Docker спрашивает реестр, что сейчас обозначает тег. Во втором запрашивает объект с заданным digest. Если содержимое удалено, получение по digest может завершиться ошибкой. Другое содержимое по тому же digest корректный клиент не примет. Закрепление digest обеспечивает точность выбора содержимого; хранение образа обеспечивается отдельно.

**Мысленный эксперимент.** Сегодня собрали коммит A с базовым `alpine:3.22`. Через месяц разработчики Alpine обновили содержимое за этим тегом. Повторная сборка A может дать другой слой и другой digest при том же Git SHA. На результат также могут влиять платформа, инструменты сборки и метаданные. Новый Git-коммит тоже не гарантирует новый digest: правка конспекта вне контекста сборки может вообще не изменить образ. Универсальной формулы «перевести Git SHA в digest» нет. Соответствие фиксируют при публикации.

**Может ли измениться тег, похожий на SHA?** Реестр воспринимает его как строку. Если теги изменяемы, издатель с соответствующими правами может привязать строку к другому содержимому. Настройка ECR Tag immutability запрещает перезаписывать защищённые теги. Карточка результата не показывает фактический режим нашего репозитория. Для deploy достаточно использовать ссылку с digest, а для выяснения происхождения полезно сохранить и SHA. [Неизменяемость тегов в ECR](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-tag-mutability.html)

## 5. Amazon ECR по частям

Amazon Elastic Container Registry хранит и выдаёт контейнерные образы. В этой работе исходники и история коммитов находятся в GitHub, временный архив — в GitHub Actions, долговременная ссылка на подготовленный к запуску артефакт — в ECR. Когда runner завершает задание, его локальное Docker-хранилище перестаёт быть способом раздать образ следующему участнику.

Разберём адрес слева направо:

| Часть | Значение в лаборатории |
|---|---|
| `998115851061` | AWS account ID проекта Rubber Ducking. Показывает, в чей реестр отправляем запрос |
| `dkr.ecr.eu-north-1.amazonaws.com` | Docker endpoint ECR в регионе eu-north-1 |
| Всё до первого `/` | Адрес реестра для `docker login` |
| `/tickets-api` | Репозиторий внутри реестра; контейнер для хранения версий нашего API |
| `:dd3a551…` | Тег внутри этого репозитория |
| `@sha256:c839…` | Альтернативный способ выбрать артефакт внутри репозитория по digest |

Ещё одно обозначение встречается в IAM: `arn:aws:ecr:eu-north-1:998115851061:repository/tickets-api`. ARN — имя ресурса в языке AWS. Его сравнивают с полем Resource в политике доступа. Для команды `docker push` требуется Docker URI выше. У роли свой ARN — `arn:aws:iam::998115851061:role/github-booking-ecr`. У IAM в этой записи пустое поле региона: IAM управляет идентичностями аккаунта, а репозиторий ECR создан в определённом регионе.

В консоли ECR **Image tags** помогает найти релиз по коммиту. **Digest** позволяет закрепить образ. **Active** показывает состояние артефакта в реестре. **Last recorded pull time: –** означает, что интерфейс в момент проверки не показывал записанного времени скачивания. Публикация в ECR сама по себе не обновляет работающий сервер.

## 6. Почему в AWS появились три аккаунта

Изначально IAM проекта показывал `Feature unavailable` при переходе в Identity providers. AWS Settings требовал сначала обновить план, затем отдельно активировать advanced features. После активации и обновления вкладки в Rubber Ducking появилась таблица `No resources to display`: доступ к разделу уже был, провайдеров ещё не создали.

| Аккаунт | Назначение | Где использовали |
|---|---|---|
| Rubber Ducking | Аккаунт ресурсов учебного проекта | Здесь ECR, провайдер GitHub и роль публикации |
| Team Management Account | Управление организацией и общими расходами | Условия плана, биллинг, управление организацией |
| Team Identity Delegated Admin | Делегированное администрирование идентичностей команды | Служебная часть организации |

Важно различать **вход человека в консоль** и **вход программы из CI**. Человек зашёл через свою учётную запись в сессию AccountFullAccessRole и оформил настройки. Позднее runner получает отдельную узкую роль github-booking-ecr. Имя человека, пароль для входа в AWS и сессия браузера runner’у не нужны. Слово Identity в названии служебного аккаунта не означает, что OIDC-провайдера для нашей роли надо создавать именно там. Настройка выполнена в аккаунте, где живут роль и ECR.

При разборе Billing мы видели приветственные кредиты. Переход на Paid допускает начисления за потребление сверх применимых кредитов, а активация расширенных функций меняет управление проектами и удаляет прежние spend limits. Это история настройки данного аккаунта; для аккаунта с уже доступным IAM начинать с активации не требуется. [Изменения при активации AWS](https://docs.aws.amazon.com/accounts/latest/reference/activate-advanced-features.html)

## 7. Провайдер, роль и две политики

Это центральное различие недели. Чтобы разбирать ошибку, сначала сформулируй вопрос, который AWS решает на конкретном этапе.

| Вопрос | Какой объект даёт ответ | Наше значение |
|---|---|---|
| Кто выпускает удостоверение для runner? | Издатель OIDC в GitHub Actions | `https://token.actions.githubusercontent.com` |
| Какому издателю и какой аудитории доверяет наш аккаунт? | IAM Identity provider типа OpenID Connect | Провайдер GitHub, audience `sts.amazonaws.com` |
| Какую роль хочет получить задание? | `role-to-assume` в workflow | `github-booking-ecr` |
| При каких условиях разрешено получить эту роль? | Trust policy роли | Издатель GitHub, нужные audience, владелец, репозиторий и ветка |
| Кто выдаёт временные учётные данные? | AWS Security Token Service, STS | Операция `AssumeRoleWithWebIdentity` |
| Какие операции разрешены полученной сессии? | Permissions policy роли | Inline policy `PushTicketsApi` |
| Может ли само задание запросить OIDC-токен у GitHub? | GitHub Actions job permissions | `id-token: write` только у publish |

### 7.1. Регистрация провайдера

В аккаунте Rubber Ducking открыли **IAM → Identity providers → Add provider → OpenID Connect**. Provider URL указывает на издателя токенов GitHub Actions. Этот адрес общий для множества репозиториев. AWS использует опубликованные издателем сведения и ключи для проверки подписанного токена. **Audience** указывает ожидаемого получателя. Для нашей интеграции выбрали `sts.amazonaws.com`. Это общие настройки для проверки удостоверений. Появление строки GitHub в списке провайдеров ещё не предоставляет ни одному заданию право загрузить образ.

### 7.2. Создание роли и trust policy

В **IAM → Roles → Create role** выбрали **Web identity**, затем созданного провайдера GitHub, аудиторию STS, владельца `kinzaz`, репозиторий `booking`, ветку `master`. На шаге Add permissions оставили выбор пустым и дали роли имя `github-booking-ecr`. Затем уточнили условие subject после диагностики. Ниже минимальная эквивалентная запись нужного правила. Это образец для понимания полей, а не дословный экспорт из AWS.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::998115851061:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:kinzaz@114291937/booking@1466382710:ref:refs/heads/master"
      }
    }
  }]
}
```

- **Principal.Federated** связывает роль с записью конкретного провайдера в этом AWS-аккаунте.
- **Action** описывает вход через удостоверение внешнего издателя. Успешный вызов создаёт временную сессию роли.
- **aud** отвечает на вопрос «для какого получателя выпустили токен?». В настройке провайдера, в токене и в условии роли должны согласоваться ожидаемые значения.
- **sub** отвечает на вопрос «какую идентичность представляет этот токен?». В нашем случае это контекст запуска для определённой ветки. `114291937` — числовой ID владельца GitHub, `1466382710` — ID репозитория. `refs/heads/master` — полное имя ссылки Git на ветку. Число `998115851061` относится к другой системе и обозначает AWS-аккаунт.
- **Version** — версия синтаксиса IAM policy. Дата не означает срок действия роли.
- Ветку проверяют дважды по разным причинам. Условие `if` решает, запускать ли задание в GitHub. Условие `sub` применяется внутри AWS независимо от текста workflow. Обязательность успешного smoke-теста задаёт `needs: check` в GitHub. STS не читает журнал тестов.

### 7.3. Политика разрешений PushTicketsApi

В **Roles → github-booking-ecr → Permissions → Add permissions → Create inline policy** добавили два правила. Inline означает, что политика принадлежит этой роли. По первому правилу можно запрашивать токен входа в ECR. По второму — выполнять перечисленные операции в конкретном репозитории.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ecr:GetAuthorizationToken",
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "ecr:BatchCheckLayerAvailability",
        "ecr:InitiateLayerUpload",
        "ecr:UploadLayerPart",
        "ecr:CompleteLayerUpload",
        "ecr:PutImage",
        "ecr:BatchGetImage",
        "ecr:ListImages",
        "ecr:DescribeImages"
      ],
      "Resource": "arn:aws:ecr:eu-north-1:998115851061:repository/tickets-api"
    }
  ]
}
```

| Разрешение | Зачем включено |
|---|---|
| GetAuthorizationToken | Получить данные входа для Docker. У этого действия нет ограничения по ARN отдельного репозитория, поэтому в первом правиле Resource равен звёздочке |
| BatchCheckLayerAvailability | Определить, какие слои уже хранятся в ECR |
| InitiateLayerUpload, UploadLayerPart, CompleteLayerUpload | Начать загрузку отсутствующего слоя, передать его части, завершить передачу |
| PutImage | Зарегистрировать манифест и тег в репозитории |
| BatchGetImage | Прочитать манифест по идентификатору образа |
| ListImages | В нашем скрипте узнать, существует ли тег этого коммита |
| DescribeImages | Прочитать метаданные опубликованного образа и записать digest в Summary |

Звёздочка в **первом** правиле относится к одной операции. Доступ к содержимому реестра определяется действиями **второго** правила с ARN tickets-api. Например, если заменить в команде push имя назначения на tickets-worker, приведённая политика не даст права PutImage в этот репозиторий. Политика также не создаёт репозиторий и не запускает контейнеры на EC2. [Права для публикации в ECR](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-push-iam.html)

## 8. Что происходит при входе, шаг за шагом

1. GitHub запускает publish для push в master после check. Задание имеет `id-token: write`. Название write означает возможность запросить OIDC-токен на стороне GitHub. Для записи исходников или образов действуют другие разрешения.
2. Action `aws-actions/configure-aws-credentials` запрашивает у GitHub короткоживущий подписанный токен. В нём есть утверждения (claims), в том числе issuer, audience и subject. Выводить целый токен в лог для диагностики не требуется.
3. Action передаёт токен и ARN желаемой роли в STS. AWS проверяет подпись, допустимость токена и соответствие политике доверия. Если subject расходится даже при правильной ветке в названии, точное сравнение не пройдёт.
4. При успехе STS выдаёт временный access key ID, secret access key и session token. Action предоставляет их последующим командам в задании. Постоянные ключи пользователя в настройках репозитория для этой схемы не создавали.
5. AWS CLI подписывает запросы этими временными данными. `aws ecr get-login-password` получает пароль для подключения Docker. Docker ожидает протокол реестра, а AWS CLI умеет подписывать обращения к AWS API; этим объясняется отдельная операция входа.
6. `docker login --username AWS --password-stdin <адрес-реестра>` читает пароль из стандартного ввода. `AWS` здесь фиксированное имя пользователя для этого способа входа. Права определяет IAM-сессия, запросившая пароль. ECR указывает срок действия своего authorization token 12 часов. Это отдельный токен со своим назначением, отличным от OIDC-токена GitHub.
7. Docker отправляет образ. ECR проверяет права на нужные действия и репозиторий. Если вход прошёл, но PutImage запрещён, задание упадёт позднее, уже на публикации. [Вход в приватный реестр ECR](https://docs.aws.amazon.com/AmazonECR/latest/userguide/registry_auth.html)

## 9. Как CI гарантирует передачу проверенной сборки

В check после проверок команда `docker compose ps -q api` возвращает ID контейнера API из первого стенда. `docker inspect --format '{{.Image}}'` берёт локальный ID образа, из которого создан этот контейнер. Тем самым workflow выбирает именно образ сервиса, обработавшего smoke-запросы, даже если в Docker есть несколько сборок с похожими именами.

Далее `docker tag` добавляет ему имя `tickets-api:$GITHUB_SHA`. Эта операция не перекомпилирует приложение. `docker save` сохраняет образ с этим тегом в `api.tar`. GitHub загружает архив как artifact `tested-api` со сроком хранения один день. Времени хранения архива достаточно для обычной последовательности заданий. Если при позднем повторе publish архив уже недоступен, нужно повторить check, чтобы заново сформировать artifact.

На другом runner задание publish скачивает архив и проверяет наличие тега в ECR. Для **нового тега** выполняются login, load, tag, push. `docker load` восстанавливает локальный образ, а второй tag добавляет полное имя назначения ECR. Команда `docker push` передаёт уже собранный объект. Это устраняет риск заново подтянуть изменившийся базовый образ между проверкой и публикацией.

Для **уже существующего тега** скрипт пропускает повторную загрузку и читает digest из ECR. Такой повтор сообщает digest ранее опубликованного объекта. Он не сравнивает содержимое прежнего объекта с новой локальной сборкой того же коммита. Также проверка наличия и push — две отдельные операции; при одновременных публикациях поведение зависит в том числе от immutability тега.

В конце `aws ecr describe-images` возвращает `imageDigest`. Запись в `GITHUB_STEP_SUMMARY` оставляет человеку пару «коммит → URI с digest». В логе нашей публикации Docker показал:

```text
dd3a551a01f33d6a2c82bceb50b0798a0885c895: digest: sha256:c839290f85a9f1dbbc7e2e9887b50ff5fae8f0245cb2280654605125152cff83 size: 855
```

Число 855 в ответе push относится к размеру опубликованного верхнеуровневого документа в байтах. В карточке ECR было 9.42 MB — это другая величина. Сверять между логом и карточкой для идентификации релиза нужно digest.

## 10. Реальная ошибка недели и порядок диагностики

После слияния первый publish остановился с сообщением:

```text
Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity
```

Из текста можно определить границу сбоя. Задание уже дошло до получения роли. До входа Docker и проверки прав на загрузку слоёв выполнение ещё не дошло. Добавление ecr:PutImage здесь ничего не исправит. Сначала открываем у роли **Trust relationships** и сравниваем провайдера, audience и ожидаемый subject.

В нашем правиле было два одинаковых значения старого формата. Повтор записи сам по себе не мешал; обе строки ожидали один и тот же неподходящий subject.

```text
Было:  repo:kinzaz/booking:ref:refs/heads/master
Стало: repo:kinzaz@114291937/booking@1466382710:ref:refs/heads/master
```

GitHub ввёл новый формат по умолчанию для репозиториев, созданных после 15 июля 2026 года. Наш репозиторий создан 21 ноября. После уточнения subject роль сохранила узкую привязку к владельцу, репозиторию и master, а следующий успешный push вернул digest. Для другого проекта следует уточнить его формат subject и ID, особенно если задание использует GitHub Environment или собственный шаблон OIDC. [Изменение формата subject в GitHub](https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens/)

| Что видим | Что проверить первым |
|---|---|
| На PR задание publish имеет статус Skipped | Это ожидаемо по условию события. Для публикации нужен push в master и успешный check |
| До smoke-теста приходит Connection refused | Запущены ли контейнеры, на каком порту опубликован frontend, завершился ли старт API |
| Smoke-тест падает на бронировании | Логи API и PostgreSQL, наличие тестового мероприятия, HTTP-ответ шага |
| Ошибка при AssumeRoleWithWebIdentity | ARN роли, провайдер, audience, точное значение sub, контекст ветки запуска |
| AWS сообщает AccessDenied для ecr:ListImages | Вход в роль уже состоялся; проверить разрешение ListImages и ARN ресурса |
| Docker сообщает об отсутствии данных входа | Был ли docker login в этом задании и совпадает ли его hostname с hostname образа |
| ECR сообщает, что репозиторий отсутствует | Проверить имя tickets-api, номер аккаунта и регион настройки AWS CLI |
| Шаг скачивания tested-api не находит artifact | Проверить шаг upload в check, имя архива и срок его хранения |

## 11. Как самостоятельно подтвердить результат

**В консоли.** Открыть в GitHub запуск для коммита слияния, проверить успешные check и publish, взять digest из Summary или строки push. В AWS выбрать Rubber Ducking → регион Stockholm → ECR → Private repositories → tickets-api → Images. Открыть тег с полным Git SHA и сравнить весь digest, включая последние символы. Именно эту проверку мы выполнили.

**Через AWS CLI**, если CLI установлен и настроена сессия с правом чтения метаданных репозитория. Это дополнительный способ повторить проверку. Команда ничего не публикует.

```bash
aws ecr describe-images \
  --region eu-north-1 \
  --repository-name tickets-api \
  --image-ids imageTag=dd3a551a01f33d6a2c82bceb50b0798a0885c895 \
  --query 'imageDetails[0].imageDigest' \
  --output text
```

**Что передать на неделю 8.** Для staging использовать полный URI с `@sha256:…` из раздела 4. Серверу потребуется собственный способ получить доступ на чтение приватного ECR. Роль github-booking-ecr создана для GitHub Actions и публикации. Настройка чтения на сервере и проверка пользователя после развёртывания — следующий этап.

### Вопросы для самопроверки

1. **Если известен только Git SHA, можно ли вычислить digest?** Нет. Нужны результат сборки и сведения реестра. В практике их связали тегом и записью в Summary.
2. **Если тег похож на хеш, почему для deploy берём digest?** Тег выбирает объект по назначенному имени. Digest проверяет конкретное содержимое независимо от того, как в дальнейшем используют имена.
3. **Почему runner после успешного теста не может сразу выполнить push в приватный ECR?** Тест подтверждает поведение приложения. ECR отдельно проверяет право выполняющего запрос субъекта на публикацию.
4. **Если провайдер создан, зачем роль?** Провайдер позволяет проверить удостоверение GitHub. Условия роли определяют, каким заданиям разрешено получить сессию и какие операции ей доступны.
5. **Почему токен с правильной audience мог получить отказ?** У роли есть и условие subject. В нашем случае в ожидаемом subject отсутствовали числовые ID.
6. **Почему нужен архив между заданиями?** Runner задания publish не имеет локального Docker-хранилища задания check. Архив передаёт проверенную сборку между машинами.
7. **Что доказывает совпадение digest из лога и карточки ECR?** В репозитории найден именно тот опубликованный индекс, идентификатор которого вернул push. Работу приложения подтвердил smoke-тест ранее; состояние работающего сервера проверят при деплое.
