# Между неделями 7 и 8. Перенос учебного стенда из Yandex Cloud в Selectel

**23 ноября 2026 года · Проект бронирования билетов · Репозиторий `kinzaz/booking`**

Мы сменили облачного провайдера и проверили результат таким способом: взяли digest, который GitHub Actions получил после публикации образа API в Selectel, зашли на новую VM и нашли в её локальном Docker образ с точно таким же digest. Это подтверждает весь путь сборки от CI до диска сервера. Запуск приложения и проверка бронирования на самом staging относятся к следующей неделе.

Предыдущие этапы: [публикация в AWS ECR](week-07-ci-ecr.md) и [переезд в Yandex Cloud](week-07-migration-yandex-cloud.md).

## 1. Что именно переехало

| Часть проекта | Было в Yandex Cloud | Стало в Selectel |
|---|---|---|
| Хранение образа API | Yandex Cloud Registry | Приватный реестр `tickets-lab` на `cr.selcloud.ru` |
| Публикация из GitHub | Задание обменивало OIDC-удостоверение GitHub на временный IAM-токен | Задание берёт реквизиты токена Selectel из окружения GitHub `staging` |
| Чтение с сервера | VM получала IAM-токен сервисного аккаунта через метаданные | Docker на VM входит в реестр по отдельному токену чтения |
| Учебная VM | `84.201.181.96`, пользователь `devops` | Новая Ubuntu 24.04, `135.106.244.116`, вход под `root` |
| Исходники, Dockerfile и проверки | GitHub | Тот же репозиторий и те же проверки |

Новый релиз собрали из Git. Для этого не требовался доступ к диску старой VM. Копирование PostgreSQL, перенос старых броней и отключение ресурсов YC не входили в подтверждённый результат. Это важно для учёта расходов: создание VM в Selectel само по себе не прекращает начисления в другом облаке.

## 2. Кто с кем разговаривает

В этой практике слово «доступ» встречалось три раза. Каждый раз соединялись разные участники.

| Откуда → куда | Чем подтверждается доступ | Зачем |
|---|---|---|
| GitHub runner → Selectel Registry | Имя пользователя и пароль токена с правом записи и чтения для `tickets-lab` | Загрузить проверенный образ |
| Mac → Ubuntu на VM | Приватный SSH-ключ на Mac и соответствующий публичный ключ на VM | Открыть терминал или выполнить команду Ansible |
| Ubuntu на VM → Selectel Registry | Имя пользователя и пароль отдельного токена чтения | Скачать конкретный образ |

**Пример.** Мы успешно вошли по SSH под `root`, но первый `docker pull` вернул 401. SSH уже подтвердил право открыть терминал в Ubuntu. Затем Docker из этого терминала обратился к другому сервису — приватному реестру. Ему понадобились отдельные учётные данные. Пароль от Linux, SSH-ключ и токен реестра выполняют разные задачи.

## 3. Как GitHub начал публиковать образ в Selectel

В панели Selectel открыли **Продукты → Container Registry**, создали реестр `tickets-lab` и во вкладке **Токены** выпустили реквизиты для Docker. Для CI выбрали доступ на запись и чтение к этому реестру. Selectel показывает два значения для входа: `username` и `password`. Имя, придуманное для токена в панели, служит подписью для человека.

В GitHub выбрали окружение **staging** и разместили там три значения:

| Поле GitHub | Имя | Содержимое |
|---|---|---|
| Environment variable | `SELECTEL_REGISTRY` | `tickets-lab`, только имя реестра |
| Environment secret | `SELECTEL_REGISTRY_USERNAME` | Выданный Selectel логин токена CI |
| Environment secret | `SELECTEL_REGISTRY_PASSWORD` | Выданный Selectel пароль токена CI |

**Что случилось при первом запуске.** Workflow собрал адрес `cr.selcloud.ru//tickets-api`. Между двумя косыми чертами должно было стоять имя реестра. Первая проверка остановила задание с сообщением `REGISTRY_NAME: Set SELECTEL_REGISTRY in repository variables`. В этот момент GitHub ещё не вызывал Docker, поэтому заменять пароль в Selectel не имело смысла. Значения лежали в окружении `staging`, а задание `publish` его не выбирало. Исправили одной строкой на уровне задания: `environment: staging`. Коммит исправления — `18e3216`, слияние — PR № 9.

**Как проходит успешный релиз:**

1. После push в `master` задание `check` собирает приложение, запускает тесты, проверяет бронирование через Nginx и обновление схемы БД.
2. На том же runner CI находит образ API, который только что проверил, даёт ему тег полного Git SHA и сохраняет через `docker save` в архив. GitHub временно хранит его как артефакт `tested-api`.
3. Задание `publish` получает другой runner, скачивает архив и входит в `cr.selcloud.ru`. Пароль передаётся в `docker login` через `--password-stdin`.
4. Для нового тега задание делает `docker load`, присваивает образу полный адрес и выполняет `docker push`. Если тег коммита уже есть, workflow читает его digest. Итоговая ссылка с digest записывается в Summary.

Архив GitHub понадобился для передачи сборки между двумя временными компьютерами. Реестр нужен для того, чтобы сервер позже мог скачать эту сборку, даже когда оба runner уже завершили работу. [Workflow проекта](../../.github/workflows/pr-ci.yml) · [Инструкция Selectel по реестру](https://docs.selectel.ru/craas/quickstart/)

## 4. Как прочитать результат push

В успешном запуске мы получили строку:

```text
f6e752763768e4c7e2704bc0cf5b067e61579dbf: digest: sha256:257479c8a90cabecd86404a14f88468f8d1ca038761c2805e3c0e0596f773988 size: 855
```

- **Git SHA слева** используется как тег и связывает образ с коммитом после слияния.
- **Digest справа** идентифицирует манифест образа по содержимому. Именно его использовали при скачивании на staging.
- **855** — размер манифеста в байтах. Слои приложения занимают отдельное место.
- **Полный адрес** состоит из хоста `cr.selcloud.ru`, реестра `tickets-lab`, имени образа `tickets-api` и digest после `@`. Одного хеша без адреса реестра Docker для этой команды недостаточно.

[Запуск Actions, опубликовавший релиз](https://github.com/kinzaz/booking/actions/runs/45071779127)

## 5. Как выбрали сервер и почему он стоит 560,37 ₽

В форме создания сначала была выбрана конфигурация с выделенными ядрами, локальным SSD и платным облачным роутером. Для учебного стенда, на котором сборку проверяет GitHub, выбрали **Shared**, сетевой HDD и один прямой публичный IPv4. Для доступа по SSH отдельный роутер в этой схеме не понадобился.

| Параметр | Фактический выбор |
|---|---|
| Сервер и зона | `tickets-staging`, Москва, `ru-7a` |
| Система | Ubuntu 24.04 LTS, x86-64 |
| Вычисления | 2 shared vCPU, гарантированная доля 10%, 2 ГБ RAM |
| Хранилище | 20 ГБ, базовый сетевой HDD |
| Сеть | Прямой публичный IPv4 `135.106.244.116` |
| Доступ | Публичный ключ `mac-id-ed25519`, соответствующий приватному `~/.ssh/id_ed25519` на Mac |
| Тип | Прерываемая VM |

Сначала попробовали создать этот сервер в `ru-2c`. Панель показала ошибку квот. Проверка по типам ресурсов выявила конкретную причину: в проекте для этой зоны базовый HDD был недоступен. В `ru-7a` квота на него была, поэтому удалось сохранить размер диска, CPU, RAM и цену. После создания дождались перехода из `BUILD` в `ACTIVE`, а публичный IP проверили на вкладке **Порты**.

**Расчёт панели на момент заказа:** CPU — 73,39 ₽, RAM — 134,13 ₽, HDD — 163,29 ₽, IPv4 — 189,57 ₽. Панель показала итог **560,37 ₽/мес.**; округлённые строки могут расходиться с итогом на копейку. Обычная VM с теми же параметрами оценивалась в 1 181,09 ₽/мес. Вариант за 300,62 ₽ давал только 512 МБ RAM и 5 ГБ диска — для совместной работы Ubuntu, Docker и PostgreSQL слишком мало запаса.

**Что значит «прерываемая».** Один период работы длится максимум 24 часа, и Selectel может остановить сервер раньше. После системного прерывания статус становится `EXPIRED`. Перед занятием такую VM нужно восстановить в панели и дождаться `ACTIVE`. Данные на выбранном сетевом загрузочном диске сохраняются. После прерывания начисления за CPU и RAM прекращаются со следующего часа, а за диск и IP продолжаются. После восстановления стоит отдельно проверить запуск сервисов. [Правила Selectel для прерываемых VM](https://docs.selectel.ru/cloud-servers/about/preemptible-servers/)

## 6. Как подключили Mac и проверили Ansible

При включённом VPN маршрут к новой VM шёл через интерфейс `utun5`. Старая настройка для адреса YC распространялась только на тот один адрес. Для Selectel на Mac добавили отдельный маршрут через шлюз текущей локальной сети:

```bash
# На Mac, в сети, где шлюз — 192.168.1.1
sudo route -n add -host 135.106.244.116 192.168.1.1
route -n get 135.106.244.116 | grep -E 'gateway:|interface:'
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519 root@135.106.244.116
```

В проверенной таблице маршрутизации адрес VM шёл через `192.168.1.1` и `en0`. После перезагрузки Mac маршрут может понадобиться добавить заново. При смене сети сначала проверяют текущий шлюз. Это настройка конкретного Mac; GitHub runner пользуется собственным сетевым маршрутом.

Внутри SSH-сессии команды `whoami` и `hostname` вернули `root` и `tickets-staging`. Затем локально проверили Ansible со строкой inventory:

```ini
[staging]
tickets-staging ansible_host=135.106.244.116 ansible_user=root
```

Получили `SUCCESS`, `ping: pong` и `changed: false`. Модуль `ansible.builtin.ping` проверяет, что Ansible может войти, найти Python и выполнить модуль на удалённой машине. Это более содержательная проверка, чем сетевой ICMP ping.

**Нюанс для следующего запуска:** на момент составления конспекта [staging.ini в текущей копии проекта](../../infra/ansible/staging.ini) содержит прежнюю цель YC — `84.201.181.96`, логин `devops`. Успешный локальный тест выполнялся с адресом Selectel. Перед запуском из CI строку выше необходимо внести в inventory той ветки, которую получит runner.

## 7. Как VM получила тот же образ

В Ubuntu установили `docker.io` из репозитория пакетов и включили Docker через `systemctl enable --now docker`. Проверка Docker Engine вернула версию `29.1.3`.

Первый `docker pull` закончился сообщением `failed to fetch anonymous token … 401 Unauthorized`. На VM проверили настройки именно для того пользователя, который выполнял команду: у `root` отсутствовал файл `/root/.docker/config.json`. Реестр приватный, а Docker попытался обратиться к нему анонимно.

**Повторение на сервере** — в SSH-сессии под `root`:

```bash
docker login cr.selcloud.ru
```

В интерактивные поля вводятся выданные Selectel `username` и `password` токена чтения с доступом к `tickets-lab`. После успешного входа:

```bash
image='cr.selcloud.ru/tickets-lab/tickets-api@sha256:257479c8a90cabecd86404a14f88468f8d1ca038761c2805e3c0e0596f773988'
docker pull "$image"
docker image inspect --format '{{json .RepoDigests}}' "$image"
```

**Что фактически проверили:** после скачивания подключились по SSH и выполнили `docker image inspect`. Docker на VM вернул в `RepoDigests` полный адрес `cr.selcloud.ru/tickets-lab/tickets-api@` с тем же digest, что и в разделе 4. Это проверка локального результата на сервере. Один лишь успешный `docker login` подтвердил бы только вход в реестр. [Как выдаются права токенам Selectel](https://docs.selectel.ru/craas/tokens/generate-token/)

## 8. Что передаём на неделю 8

У нас есть воспроизводимая сборка API, публикация после тестов, приватный реестр, доступная по SSH staging-VM и точная ссылка на уже скачанный релиз. Следующая контрольная точка — получить `pong` **из GitHub Actions**. Для этого нужно обновить inventory, разместить на VM публичный ключ, соответствующий CI-секрету `STAGING_SSH_KEY`, и обновить `STAGING_KNOWN_HOSTS` проверенным ключом хоста Selectel. Успешный вход с личного Mac подтверждает только доступ с Mac. [Существующий workflow staging-ping](../../.github/workflows/staging-ping.yml)

После этого начинается деплой: Ansible запускает компоненты стенда, API использует зафиксированный digest, smoke-тест создаёт бронь через Nginx, а учебный сбой проверяет откат. На момент миграции опубликован именно образ API. Его наличие на диске не подтверждает запуск PostgreSQL, worker, frontend или всей системы бронирования.
