# Между неделями 7 и 8. Переезд учебного стенда из AWS в Yandex Cloud

**22 ноября 2026 · Проект бронирования билетов · Репозиторий `kinzaz/booking`**

К концу недели 7 GitHub Actions умел проверять приложение и публиковать образ API в Amazon ECR. Когда учебный аккаунт AWS заблокировали, мы заново построили путь от исходного кода до сервера в Yandex Cloud. Теперь GitHub публикует проверенный образ в **Yandex Cloud Registry**, а виртуальная машина **tickets-staging** скачивает его по digest. С Mac на сервер можно зайти по SSH при включённом VPN.

Это точка старта недели 8. Образ скачан на staging, но приложение ещё предстоит развернуть и проверить через Nginx. История прежней VM и содержимое её PostgreSQL остались за пределами этого переноса. В Git есть схема БД, миграции и демонстрационные данные. Для восстановления конкретных старых броней потребовался бы дамп или снимок с данными.

| Сервисный аккаунт VM | `tickets-staging-vm`, ID `ajeok43kdpstc24pasdu` | Роль `cloud-registry.artifacts.puller` на реестр позволяет скачивать образы |

| Пользователь Ubuntu | `devops`, OS Login выключен | Вход по SSH-ключу, права в Linux определяются настройками пользователя |

Имена помогают человеку выбрать объект в консоли. ID указывает конкретный объект в workflow или адресе образа. У аккаунта публикации, аккаунта VM и реестра три разных ID. Знание любого из них само по себе не даёт доступа.

Есть и три разных входа. **GitHub → облако** использует удостоверение задания CI. **VM → реестр** использует удостоверение, привязанное к виртуальной машине. **Mac → Ubuntu** использует SSH-ключ человека. Именно поэтому изменение роли реестра не помогает при ошибке входа по SSH, а смена SSH-ключа не исправляет ошибку получения IAM-токена.

## 3. Как GitHub публикует проверенный образ

1. На pull request выполняется задание `check`. Оно собирает и тестирует Go-пакеты, поднимает Compose-стенд и вызывает smoke-тест через Nginx. Тест проверяет готовность, создаёт бронь, повторяет запрос с тем же ключом идемпотентности, читает статус и отменяет бронь.
2. Отдельно CI поднимает базу со схемой из миграции 001, помещает в неё контрольную запись и запускает API. После перехода на 002 проверяется и регистрация миграции, и сохранность значения в старой записи.
3. После push в `master` проверки выполняются снова. CI находит образ работающего контейнера API, присваивает ему тег с полным Git SHA, делает `docker save` и загружает архив в GitHub Actions как артефакт `tested-api` со сроком хранения один день.
4. Задание `publish` зависит от успешного `check` и работает на другом runner. Оно забирает архив. На pull request статус `publish: Skipped` ожидаем. Такая граница не даёт обычной проверке PR права публиковать релиз.
5. Для нового тега `publish` загружает архив через `docker load`, добавляет тег с адресом Cloud Registry и выполняет `docker push`. Повторной сборки между тестом и публикацией нет. Если тег этого коммита уже существует, workflow получает его digest и использует существующую публикацию.
6. В конце workflow читает digest манифеста из реестра, проверяет формат `sha256` и помещает ссылку для развёртывания в GitHub Step Summary.

**Зачем два хранилища?** Артефакт GitHub передаёт файл между двумя заданиями одного запуска. Cloud Registry хранит релиз, к которому staging может обратиться позже. Успешный smoke-тест относится к временному стенду CI. На staging его нужно будет запускать заново после деплоя. [Workflow](../../.github/workflows/pr-ci.yml) · [Smoke-тест](../../deploy/smoke.sh)

## 4. Как устроен вход GitHub без постоянного ключа

В Yandex IAM настроили федерацию сервисных аккаунтов. Её задача — проверить, кто выдал удостоверение и какому внешнему заданию разрешено действовать от имени `github-booking-publisher`.

| Поле | Значение для нашего проекта | Что проверяется |
|---|---|---|
| Issuer, `iss` | `https://token.actions.githubusercontent.com` | Удостоверение выпустил GitHub Actions |
| JWKS | `https://token.actions.githubusercontent.com/.well-known/jwks` | Адрес открытых ключей для проверки подписи GitHub |
| Audience, `aud` | `https://github.com/kinzaz` | Получатель, для которого action запросил удостоверение |
| External subject, `sub` | `repo:kinzaz@114291937/booking@1466382710:ref:refs/heads/master` | Привязка к владельцу, репозиторию и ветке. Числовые ID входят в фактический формат этого проекта |

В workflow разрешение `id-token: write` даёт заданию возможность запросить OIDC-токен у GitHub. Action `yc-iam-token-fed` передаёт этот токен и ID сервисного аккаунта в Yandex IAM. После проверки привязки IAM возвращает краткоживущий токен. Docker получает его через стандартный ввод с именем пользователя `iam`. Какие операции пройдут после входа, определяет роль аккаунта на реестре.

**Ошибка, которую действительно встретили.** Первый запуск закончился сообщением `401 invalid_client: No matching federated credentials for specified service account, issuer and external subject`. В workflow попал другой ID сервисного аккаунта. Мы открыли карточку `github-booking-publisher` и исправили `yc-sa-id` на `aje195o8ms9d7r1r9ll1`. ID записали прямо в workflow, поэтому отдельная GitHub variable не нужна. На случай повторения добавили шаг, который при ошибке выводит только `iss`, `aud` и `sub`. После слияния исправления публикация прошла. [Федерация с GitHub](https://yandex.cloud/ru/docs/tutorials/serverless/ci-cd-github-functions)

## 6. От создания VM до рабочего SSH

В Compute Cloud создали VM, назначили ей публичный IPv4 и привязали `tickets-staging-vm`. При создании Ubuntu через cloud-init появился пользователь `devops` с публичным ключом. В самой VM сервисный аккаунт нужен для обращений к облачному API. SSH-клиент на Mac отдельно доказывает Ubuntu владение приватным ключом.

При проверке последовательно встретились **две независимые неисправности**. Устранение первой позволило увидеть вторую.

### Сначала выясняли, доходит ли соединение до SSH

На Mac выполнили:

```bash
ssh -v -o ConnectTimeout=30 devops@84.201.181.96
```

В выводе были `Connection established` и `Local version string SSH-2.0-OpenSSH_9.9`, затем `Connection timed out during banner exchange`. Клиент открыл TCP-соединение и отправил своё приветствие. Приветствие SSH-сервера до клиента не дошло. Подбор логина или ключа на этой стадии ничего не проверяет.

В консоли Yandex Cloud сверили публичный IP и логин с подсказкой в карточке VM. В выводе последовательного порта нашли завершение cloud-init, ключ пользователя и отпечатки ключей хоста. У привязанной группы безопасности было входящее правило `Any` для `0.0.0.0/0`, то есть порт 22 уже был разрешён. Через прямое соединение без VPN Mac получил приветствие сервера. Точное место потери трафика внутри маршрута VPN мы не установили.

SSH предложил сохранить ED25519-ключ **сервера**. Перед подтверждением сравнили его отпечаток с последовательным портом VM:

```text
SHA256:dz0AC/kjTLYiwBN2dIqK6EzoAiNNpvinFVUbWj5589M
```

Совпадение подтвердило личность сервера. После ответа `yes` SSH записал ключ хоста в `known_hosts` на Mac. Затем началась отдельная проверка личности пользователя.

### Затем восстанавливали вход пользователя devops

Ошибка сменилась на `Permission denied (publickey)`. Mac по умолчанию предлагал `id_ed25519`. По отпечатку публичного ключа из журнала VM выяснили, что при создании сервера для `devops` был установлен другой ключ — `devops_learning`. Явно выбрали его через `ssh -o IdentitiesOnly=yes -i ~/.ssh/devops_learning …`. Клиент запросил парольную фразу. Проверили ключ локально, исключив сервер и сеть из эксперимента:

```bash
ssh-keygen -y -f "$HOME/.ssh/devops_learning" >/dev/null
```

Сообщение `incorrect passphrase supplied to decrypt private key` означало, что введённая фраза не расшифровывает приватный ключ на Mac. Этой же командой для `$HOME/.ssh/id_ed25519` подтвердили, что второй ключ доступен. Для восстановления на сервер передали его **публичную** часть из файла с расширением `.pub`.

В карточке работающей VM открыли **Редактировать → Метаданные → user-data**. Сохранили исходную конфигурацию и дополнили её временным блоком `bootcmd`: при загрузке он проверял существование `/home/devops/.ssh/authorized_keys` и добавлял строку нового публичного ключа, если такой строки ещё не было. Предыдущие ключи сохранялись. Перезапустили VM через меню **Ещё → Перезапустить**, дождались завершения cloud-init и вернули исходное значение `user-data`, убрав команду восстановления. Команда меняла файл на загрузочном диске, поэтому удаление временной инструкции из метаданных не отменяло уже сделанную запись.

В журнале было предупреждение о проверке схемы cloud-init. Сам статус Running и завершение cloud-init были промежуточными признаками. Подтверждением восстановления стал успешный SSH-вход с Mac новым ключом. [Инструкция по восстановлению доступа](https://yandex.cloud/ru/docs/compute/operations/vm-connect/recovery-access)

### Как сохранили VPN для остального трафика

В настройках iProxy не нашли исключения для одного адреса. В таблице маршрутизации Mac увидели VPN-интерфейс и обычный шлюз `192.168.1.1` через `en0`. На Mac добавили маршрут к одному адресу VM:

```bash
sudo route -n add -host 84.201.181.96 192.168.1.1
route -n get 84.201.181.96 | grep -E 'gateway:|interface:'
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519 devops@84.201.181.96
```

Более точный маршрут к одному хосту имеет приоритет перед маршрутом по умолчанию. SSH заработал с включённым VPN. Это локальная настройка Mac. После перезагрузки Mac маршрут потребуется установить снова. При смене Wi-Fi сначала уточни шлюз, а при смене публичного IP VM подставь актуальный адрес. Чтобы убрать именно наше исключение, выполни на Mac `sudo route -n delete -host 84.201.181.96`.

## 7. Как VM получила образ без ключа от GitHub

Следующие команды выполняются **внутри Ubuntu после SSH-входа**. На Mac адрес службы метаданных не даст удостоверение этой VM.

```bash
sudo apt-get update && sudo apt-get install -y docker.io jq curl
sudo systemctl enable --now docker
```

Привязанный сервисный аккаунт позволяет получить краткоживущий IAM-токен через службу метаданных VM. Заголовок указывает тип запроса, `jq` извлекает из JSON только значение токена, а `--password-stdin` передаёт его Docker без вывода в терминал. `pipefail` помогает заметить ошибку любого звена.

```bash
set -o pipefail
curl -fsS -H 'Metadata-Flavor: Google' \
  http://169.254.169.254/computeMetadata/v1/instance/service-accounts/default/token \
  | jq -er '.access_token' \
  | sudo docker login --username iam --password-stdin registry.yandexcloud.net
```

После `Login Succeeded` скачали релиз из раздела 5. Здесь и при входе использовали `sudo docker`, так что обе команды работают с учётными данными одного пользователя Linux.

```bash
image='registry.yandexcloud.net/cn1gpsf8uv1vr8qj62s6/tickets-api@sha256:c44a3c53c65c78414fac7ce93f3564617c39ae7f32fe0cae904d75b639a45a3d'
sudo docker pull "$image"
# Для повторной локальной проверки после скачивания
sudo docker image inspect "$image" --format '{{json .RepoDigests}}'
```

Успешный pull подтверждён при прохождении этапа. Теперь образ есть в локальном хранилище Docker на VM. При следующем обращении к приватному реестру после истечения токена вход повторяют. Запуск контейнера, подключение базы, применение миграций и проверка бронирования на staging — отдельные операции. [Аутентификация Docker в Cloud Registry](https://yandex.cloud/ru/docs/cloud-registry/operations/docker/authentication)

## 8. Как локализовать сбой при повторении

| Где остановилось | Что уже известно | Что проверить следующим |
|---|---|---|
| На PR `publish` пропущен | Сработало условие workflow | Для публикации открыть запуск push в `master` после слияния |
| `401 invalid_client` в шаге получения IAM-токена | До Docker login выполнение ещё не дошло | ID аккаунта публикации, привязку федерации и фактические `iss/aud/sub` |
| Токен получен, push отклонён | GitHub прошёл проверку доверия | Адрес реестра и роль pusher у аккаунта публикации |
| SSH завис до `Remote protocol version` | Аутентификация пользователя ещё не началась | Публичный IP в консоли, группу безопасности, журнал загрузки и маршрут с Mac |
| SSH показал ключ хоста, затем `Permission denied (publickey)` | SSH-сервер ответил | Логин, ключ в `authorized_keys`, выбор `-i` и локальную разблокировку ключа |
| На VM ошибка получения токена из метаданных | Запрос не дошёл до авторизации в реестре | Выполняется ли команда внутри VM и какой сервисный аккаунт указан в карточке |
| На VM login успешен, pull отклонён | Docker получил учётные данные | Роль puller на конкретный реестр, имя образа, digest и одинаковое использование sudo |
| Pull успешен, сайт недоступен | Образ скачан | Проверять запуск и конфигурацию сервисов уже в рамках деплоя недели 8 |

## 9. Что передаём на неделю 8

**Готово:** CI проверяет приложение, публикует API по коммиту и сохраняет digest. Есть staging-VM, проверенный SSH-вход с Mac и подтверждённый путь чтения из приватного реестра. Для первого релиза берём ссылку из раздела 5.

**Что предстоит сделать по roadmap:**

1. Подготовить inventory staging, доступ с runner и Ansible playbook для Ubuntu. Локальный маршрут Mac относится только к этому Mac. Прежняя роль PostgreSQL использует пакет `postgresql16-server`, команду `postgresql-setup` и пути Amazon Linux — их нужно адаптировать, если выбираем установку БД этой ролью.
2. Развернуть согласованный набор компонентов. Сегодня опубликован API. В имеющемся Compose для API указан `build`; для релиза staging понадобится передать `image` с digest, а также определить, как запускаются PostgreSQL, worker и frontend с Nginx.
3. Вызвать playbook из CI, сохранить журнал и запустить smoke-тест на адресе staging. Именно успешное создание брони через Nginx подтвердит работу приложения после деплоя.
4. Сохранить последнюю рабочую версию, выпустить учебную поломку создания брони, обнаружить её smoke-тестом и выполнить откат. Разобрать запуск того же playbook через шаблон задания AWX или Ansible Automation Platform.
